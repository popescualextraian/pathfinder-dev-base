# Architect

Keep a light architecture description of the project that agents and people read, check plans
against it before they are applied, and check the code against it. The doc directs; it does not
teach. Name the style, pin the project's own choices, list the rules. Write only what the code
does not show: no field lists, routes or class inventories, no textbook explanations.

Principles, in priority order: make it work, YAGNI, least surprise, KISS, be consistent, DRY,
clean code, SOLID, design patterns; boy scout rule; make it fast last. They apply to the doc too.

## Where the files live

All in `docs/architecture/` of the project:

- `architecture.md`: the top page; front matter (style, parts, layers, modules, boundaries,
  principles, patterns, exceptions) is machine-read. You write it; people review it.
- `components/<id>.md`: one page per component. `flows/<id>.md` and `decisions/<n>.md`: optional.
- `omitted.yaml`: paths owned by no component, each with a reason.
- `catalog/`: the project's own catalog entries, optional.
- `index.md`, `model.json`, `rules.depcruise.cjs`: generated by `agentic-arch build`.
- `reviews/full.json` and `reviews/plans/<slug>.json`: written by you in review and plan mode.

This skill's `schema/*.json` are the truth for every front matter and review file. Read
`reference/pages.md` before writing a page; start every page from `templates/`.

## Who writes what

- You write the pages, `omitted.yaml` and the review JSON files.
- You never write `model.json`, `index.md` or `rules.depcruise.cjs`; `agentic-arch build` does.
- After every edit run `agentic-arch build`, then `agentic-arch check`, and fix every line `check`
  prints until it prints `architect: ok`. Lines starting `warn:` are not problems; read them. A
  review JSON you wrote is valid only once `check` passes on it.
- `agentic-arch sync` mirrors the index into `.github/copilot-instructions.md` for Copilot.
- `agentic-arch affected <range>` maps each changed file: `component <id> <file>`, `omitted`, `unclaimed`.
- `agentic-arch deps [--affected <sha>]` runs dependency-cruiser with the generated rules and
  prints the findings as a JSON array. It exits 1 when it has findings (not an error), 0 for none
  and 2 on an error or when dependency-cruiser is missing.

## The catalog

Styles, principles, patterns and templates are looked up by id; the last one found wins:
built-in (this skill's `catalog/`), then the overlay (`/opt/agentic/catalog/architect/`), then the
project (`docs/architecture/catalog/`). Read the entries the doc names before judging against them.

## Findings

Every finding has a stable id without line numbers: `<rule>/<component>/<slug>`, for example
`dry/order-service/copied-price-rule`. `agentic-arch deps` builds its own ids as
`<family>/<from-component>/imports-<to-component>`; keep them as they are. Status:

- `open`: found now.
- `fixed`: was open, no longer found. Keep it for one review, then drop it.
- `accepted`: its id is in the `exceptions` of `architecture.md`.

No nagging: an accepted finding is shown as accepted, never as new; a finding keeps its id.

## Modes

### seed

Once per repository. Follow `reference/seed.md`.

1. Read the layout, the existing CLAUDE.md and `docs/`. Detect the style and the layers with the
   catalog's `detect` hints.
2. Define the components (aim for 5 to 30 top-level ones). Write `architecture.md`, the component
   pages and a few main flows, all `status: draft`. Put unowned paths into `omitted.yaml`.
3. Add `@docs/architecture/index.md` to CLAUDE.md (`templates/CLAUDE-snippet.md`); do not rewrite
   the rest of CLAUDE.md. Run `agentic-arch build`, `agentic-arch sync`, `agentic-arch check`.
4. Run a first full review (`review --full`).
5. Summarise: what was written, the detected style and why, and "Needs a human": uncertain style
   or layer calls, and the CLAUDE.md statements the doc now holds.

### update [<range>]

After a change. Without a range use `$(git merge-base HEAD <default branch>)`.

1. Run `agentic-arch affected <range>`. For each component listed, read the diff of its files and
   its page; correct only what the diff contradicts.
2. Each `unclaimed` file gets an owner: a component's `sources`, a new component, or
   `omitted.yaml` with a reason.
3. Delete the plan reviews in `reviews/plans/` this branch has implemented (git keeps them). Drop
   or rename a removed or renamed component's entries in `reviews/full.json` and plan reviews.
4. Run `agentic-arch build`, `agentic-arch sync`, `agentic-arch check`. Summarise the changes.

### plan <plan-file>

Review a plan or spec against the doc before it is applied. Follow `reference/plan-review.md`.

1. Read the plan, `architecture.md`, the pages of the components it touches and the catalog
   entries the doc names.
2. List each component the plan touches as new, changed or removed with one line; a new one gets
   its proposed part, module, layer and summary.
3. Check every principle and rule against the plan. A break names the rule, why the plan breaks
   it, and the simpler alternative; one whose id is in `exceptions` stays with status `accepted`.
4. Give a rough size: S, M or L.
5. Write `reviews/plans/<slug>.json`, run `agentic-arch check`, and print a short summary for the
   person and the agent.

Plan mode is advisory: it writes the review and stops. It never blocks the work, and it never asks
a question inside a detached task; it states what it found and moves on. The person reads the
review and either changes the plan or accepts a break with `accept`.

### review [--full]

The code against the doc and its rules. Follow `reference/full-review.md`.

1. Deterministic checks first: `agentic-arch deps` (TS/JS), then jscpd for DRY and knip for YAGNI
   only when the project already has them.
2. Then read the code for what tools cannot see: business logic in the API layer, logic copied
   across components (one copy per database type instead of one service with an adapter per data
   source), a component doing two jobs.
3. Incremental by default: only components whose sources changed since the commit each was last
   reviewed at. `--full` re-checks every component.
4. Merge with the previous `reviews/full.json` and the exceptions, write it, run
   `agentic-arch check`, and summarise new, fixed and accepted findings.

### accept <finding-id> "<reason>"

Record an accepted break. Find the finding in the reviews, add `{id, rule, component, reason}` to
`exceptions` in `architecture.md` (with `plan: <slug>` when it comes from a plan review), add one
line to the body's Exceptions section, set the finding's status to `accepted`, then run
`agentic-arch build` and `agentic-arch check`.

### new <template>

Start a new project from a catalog template: resolve `templates/<template>` in the catalog, write
`docs/architecture/architecture.md` from it with the project's name and description, add the
CLAUDE.md line, then run `agentic-arch build`, `agentic-arch sync`, `agentic-arch check`.
Components come later, as the code appears.

### audit

Change nothing. Run `agentic-arch check`, then report what a script cannot see: pages that copy
the code or teach the textbook, claims the code contradicts, components doing two jobs, rules in
`architecture.md` the code no longer follows, and stale exceptions.

## Guardrails

- The code wins over the doc. Under-claim rather than over-claim.
- Write only `docs/architecture/`, the CLAUDE.md import line and `.github/copilot-instructions.md`
  (through `agentic-arch sync`). Do not commit unless asked.
- Never write or change an exception or a decision on your own outside `accept`; list a proposal
  under "Needs a human".
- Plain, results-only prose in full sentences; no process narrative.
